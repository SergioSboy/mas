# Показ проекта за 5 минут

## До занятия

1. Откройте `presentation/SQL_Agents_PostgreSQL.pptx` в PowerPoint или Keynote и проверьте шрифты, таблицы и график. Презентация должна быть открыта к началу выступления.
2. Откройте `results/postgres_prepared/report.html` в браузере. Заранее найдите Single T5, MAS T5 и MAS T3. Раскрывающиеся разделы показывают таблицу, SQL, график и историю чёрной доски.
3. Заранее выполните `docker compose run --build --rm tests` и `docker compose run --build --rm app`, если нужно убедиться в запуске. Локальный Python не нужен. Во время защиты используйте уже подготовленные результаты.
4. Загрузите PPTX до начала занятия. При переносе проекта переносите весь архив: HTML использует соседние CSV и JSON. Сам HTML и его графики открываются без сети.
5. До 22 октября обновите «Личный вклад» реальными действиями участников. Сейчас это честно обозначенное предложение по распределению, а не подтверждённый факт.
6. Если преподаватель требует именно работающие LLM-варианты и их эмпирические метрики, до защиты выполните live-прогон со своим ключом по README. Подготовленный demo этого требования полностью не заменяет.

## Речь и тайминг

### Слайд 1. Тема — 20 секунд, Сергей

Мы сравниваем три способа отвечать на вопросы к базе продаж: готовый workflow, одиночного агента и команду с разделением ролей. Нас интересует, насколько правильным получается ответ и сколько он требует времени и ресурсов. Сейчас подготовлен небольшой воспроизводимый каркас. Показываем автономный demo, реальные вызовы LLM ещё предстоит измерить.

### Слайд 2. Три варианта — 30 секунд, Сергей

Workflow выбирает готовый SQL по типу вопроса и строит отчёт. Одиночный агент сам формирует запрос, получает результат или ошибку базы, затем пишет сводку. MAS разделяет работу между Planner, SQL Agent, Analyst и Critic. Все варианты используют одинаковые данные и инструменты. Это позволяет менять архитектуру, сохраняя общую постановку задачи. В demo ответы модели заменены фиксированными учебными ответами, а в live предусмотрен настоящий API.

### Слайд 3. Архитектура — 35 секунд, Александра

Агенты обмениваются информацией через чёрную доску. Planner записывает подзадачи и порядок работы. SQL Agent формирует запрос, инструмент PostgreSQL возвращает таблицу. Analyst получает данные и рассчитанную статистику, выбирает график и делает сводку. Critic проверяет запрос и отчёт. Если он находит ошибку, замечание сохраняется в общем состоянии, Planner получает его при следующей попытке. В журнале видны все эти действия. Эталонные ответы агентам недоступны.

### Слайд 4. Правила сравнения — 35 секунд, Сергей

Всем вариантам доступны один набор вопросов, одна схема и одинаковые бизнес-правила. В live для одиночного агента и всех ролей MAS выбирается одна модель. На решение задачи общий предел — двенадцать вызовов, шестнадцать тысяч токенов, две попытки и сто двадцать секунд. Проверяем первый кандидат и итог после исправлений. Успех требует правильной таблицы, подходящего типа графика и сводки с подтверждаемым числом. Смысл всей сводки дополнительно проверяет человек. Ошибки и остановки из измерений не исключаем.

### Слайд 5. Данные и вопросы — 25 секунд, Александра

Мы создали базу из сорока восьми заказов и шести покупателей. Есть отмены и повторяющиеся причины возврата. Шесть задач проверяют выручку по месяцам и категориям, средний чек, уникальных покупателей, общую выручку и долю возвратов. Справа пример результата первого SQL-запроса. Для этих вопросов одного итогового запроса достаточно, поэтому проект остаётся небольшим.

### Слайд 6. Измерения — 45 секунд, Сергей

Таблица содержит фактически выполненные измерения demo. Workflow решил пять задач из шести сразу. У одиночного агента четыре первых успеха и пять итоговых. У MAS четыре первых и шесть итоговых. Вызовов заглушки было тринадцать и тридцать соответственно. Токены и стоимость API равны нулю, потому что модель не вызывалась. Время измеряет только локальное выполнение. Ошибки специально заданы сценарием, поэтому эти результаты проверяют механизм переделок, но не доказывают преимущество MAS над настоящим одиночным LLM-агентом.

### Слайд 7. Конкретные случаи — 45 секунд, Александра

T1 все три варианта решают успешно. В T3 вместо total указано несуществующее поле amount. PostgreSQL сообщает об ошибке, и оба агентных варианта исправляют запрос. В T5 запрос выполняется, но без фильтра статуса учитывает отменённые заказы. Одиночный агент принимает семнадцать тысяч четыреста девяносто пять. Правильное значение — пятнадцать тысяч двести шестьдесят. Demo-Critic обнаруживает пропуск фильтра и запускает исправление. T6 показывает ограничение workflow: для возвратов шаблона нет. Эти случаи можно раскрыть в подготовленном отчёте, где виден SQL и журнал.

На этом слайде при необходимости покажите **один** заранее раскрытый случай MAS T5 в браузере за 10–15 секунд вместо части устного объяснения. Новый прогон не запускайте.

### Слайд 8. Следующий эксперимент — 35 секунд, Сергей

Дальше выбираем реальную модель и фиксируем её точный ID и тарифы. Запускаем шесть задач по пяти повторов для трёх вариантов. Получится девяносто запусков. Собираем usage API, стоимость и время всех попыток, вручную проверяем сводки. Затем расширяем скрытый набор и сравниваем MAS с Critic и без него при одинаковом общем бюджете. Так можно проверить, полезна ли сама верификация и оправдывает ли она дополнительные затраты.

### Слайд 9. Личный вклад — 30 секунд, Александра

Сейчас указано предлагаемое распределение работы над подготовленным с помощью ИИ каркасом. Сергей проверяет workflow, одиночного агента и подключение модели. Александра проверяет MAS, задачи, метрики и разбор ошибок. До двадцать второго октября мы должны заменить распределение конкретными реально выполненными действиями. Каркас уже позволяет провести такой эксперимент и сохранить воспроизводимые результаты.

**Всего: 300 секунд.** После выполнения реальных задач замените текст последнего слайда и соответствующую речь, сохранив тайминг.

## Короткие ответы на вопросы

**Это уже настоящее сравнение LLM?** Нет. Это работающий экспериментальный каркас с автономным сценарием и реализованным API-режимом. Представленные числа относятся к demo. Для вывода об LLM нужны live-прогоны.

**Почему у workflow нет T6?** Это намеренно ограниченный базовый способ. Он показывает границу покрытия шаблонами. На следующем этапе стоит добавить шестой шаблон и отдельно оценивать покрытие и качество, иначе сравнение смешивает эти факторы.

**Почему четыре роли — это агенты, если модель одна?** В live каждая роль — отдельный вызов модели со своей инструкцией и областью ответственности. Они читают общее состояние и меняют ход работы через замечания. В demo эти вызовы заменены учебными ответами.

**Как исключается подсказка правильного ответа?** Эталонный SQL находится в отдельном оценщике, его результаты не передаются в состояние агента. Оценщик работает только после завершения решения.

**Что означает «с первой попытки»?** Правильность первого кандидата до исправлений. Ошибка первого SQL считается первой неудачей. У MAS кандидат фиксируется до Critic, итоговый успех требует принятия Critic.

**Что именно считает Analyst?** Общий инструмент вычисляет число групп, сумму, среднее по группам, минимум и максимум. Роль Analyst использует эти числа для сводки и выбора графика. Сумма средних чеков или долей не интерпретируется как бизнес-показатель.

**Есть ли защита базы?** Отдельная роль чтения без прав записи, транзакция READ ONLY, серверный statement_timeout и ограничение объёма результата. Проект использует искусственную базу. Это не полноценная промышленная SQL-песочница.

**Может ли Critic ошибаться?** Да. В demo он проверяет узкое правило фильтра статуса, в live рассуждает модель и может пропустить или выдумать ошибку. Поэтому есть независимый оценщик, общий лимит и следующий эксперимент без Critic.
